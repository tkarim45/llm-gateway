LLM Gateway — Architecture

The layer a platform team puts between every internal app and the model providers. One request path, every production concern: auth, rate limiting, quotas, failover, streaming, metering, audit.

Rate limit is not the same thing as quota

  • • the token bucket bounds burst pressure (requests/sec) and answers 429 with a Retry-After header
  • • the quota bounds total spend (tokens) and answers 402 when the budget is exhausted
  • • a tenant can be well inside their rate limit and still out of budget, so production billing needs both
  • • auth comes first and answers 401, so an unknown key never reaches either check

Failover, verified against real infrastructure

  • • a demo run puts a deliberately dead primary in front of real AWS Bedrock: 200 OK, served by bedrock, attempts 2
  • • the client never saw the outage; the gateway absorbed the failed attempt and metered the real token usage
  • • streaming fails over only BEFORE the first byte, because replaying a half-sent stream would duplicate or contradict it
  • • mid-stream failures surface as an SSE error event, an honest limitation rather than a hidden one
  • • providers are one interface (complete / complete_stream returning text + Usage), so adding OpenAI or vLLM is one class

Metered and auditable without becoming a PII store

  • • per-tenant token and USD metering, readable at /v1/usage alongside quota consumed
  • • the audit record carries request id, tenant, provider, tokens, cost, latency and status
  • • prompts are never audit-logged: enough for compliance and debugging, without the log becoming the liability
  • • 8 offline tests cover 401, 429 + Retry-After, 402, failover, 502-when-all-down, metering math, tenant-scoped audit and SSE
